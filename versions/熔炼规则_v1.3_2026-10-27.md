## 一、熔炼诊断：v4.5 割裂在哪

v4.5 的问题不是规则错误，而是**组织方式是拼接而非熔炼**。八处具体割裂：

| # | 割裂点         | 表现                                                                 |
| - | ----------- | ------------------------------------------------------------------ |
| 1 | 时间观分裂       | 四层周期（基本面时钟）与情绪周期（资金/情绪时钟）各自成表，「现在几点」在不同章节口径不一，未说明两钟如何耦合            |
| 2 | 离场规则三套并存    | 第十一章四层离场、14.5 三档均线阶梯、14.6 龙头卖点表，靠 14.7 裁决表**压制**冲突，而非用统一原理**消解**冲突 |
| 3 | 信号语言不通      | 信号 A/B、箱体突破失败、大阴线预警、五维检查、情绪七阶段各说各话，没有一套共同词汇                        |
| 4 | 仓位规则按优先级拼接  | 执行纪律 11 条＋双账本＋风格内限额＋裁决表，本质是同一份风险预算被切成多张表，互为「仲裁」关系                  |
| 5 | 第十四章是「附上去的」 | 14.7 裁决表、14.8 附加输出项是外来件特征：先收进来，再用规则压住                              |
| 6 | 双通道缺校验汇合点   | 基本面通道（一至四章）与量价通道（十四章）只在第七章风格表相遇一次即分叉，之后互不过问                        |
| 7 | 本能反应两表并存    | 「十条本能反应」＋「融合层补充六条」未合并去重                                            |
| 8 | 进化机制四处分散    | 预测账本（第九章）、证据等级（第十二章）、假设登记簿（knowledge/）、周度学习（作业层）没有形成单一新陈代谢回路       |

**熔炼方法**：不增删任何一条已验证规则，而是找出全部体系的**公共不变量**（公理），把每套体系还原为公理在不同尺度、不同场景上的**投影**。规则冲突在拼接式组织里需要仲裁，在公理化组织里自然消失——因为它们本来就是同一个方程在不同条件下的解。

## 三、精炼炉：持续熔炼的标准工序

主操作系统是持续融合体系；熔炼是其核心工序。炉子有**两类进料**：整炉进料（收进一套新体系）与续炉进料（各体系持续涌来的新知识）。每次分析用哪套口径，由《熔炼系统》十一 体系选择协议 决定。**何时执行哪道工序，由作业层（`作业节奏.md`）安排；本文件只定义工序本身。**


> **拆分与重编号注记**：本文件章节源自《熔炼体系》〇/八/九；2026-10-18 拆分时先沿用旧号，同日重编号为一/二/三（9.1→3.1、9.2→3.2、9.3→3.3、8.1→2.1）；体系选择协议现为《熔炼系统》十一 体系选择协议。新旧对照见 3.3 台账「重编号」行；**今后任何编号变更一律走第四章规范办理**。
### 3.1 两类进料

| 进料类型 | 对象 | 频率 | 流程 |
|---|---|---|---|
| **整炉进料** | 一套新体系（未来的第 N 家体系） | 低频 | 入库 → 还原 → 归位 → 验证 → 熔入（3.2 五步） |
| **续炉进料** | 已入库体系的新知识：风轻云淡知识库升级（v3.2 → v3.3 …）、波哥新增月份复盘、新的行业研究与专题、新的外部理论/大师著作、新的实盘教训 | 日常、小批量 | 还原 → 归位 → 验证 → 熔入（体系已在库，省去入库步骤） |

续炉进料的日常化落在 `作业节奏.md` 的周度时段：每周末至少处理一批新进料，走完「还原为公理投影 → 归位到引擎对应层 → 可疑参数降级进假设登记簿 → 通过后熔入并清渣」，并在日志登记进料来源与熔入位置。**熔炉的常态不是大炼，而是添料：单次小、批次勤、每批必留痕。**

### 3.2 整炉进料五步

1. **入库**：原样保留到 `knowledge/styles/<中文体系名>/`，自带 README（来源边界、证据等级、隔离规则）。
2. **还原**：把新体系拆成公理投影——它调用哪几条公理（A0—A5）？工作在哪个尺度（3.3 哪几行）？相位表上覆盖哪几格？参数哪些已验证、哪些是叙事？
3. **归位**：把可执行规则映射进引擎的对应层。与现有规则的表面「冲突」优先尝试用第五章方程或第六章函数消解（同一变量不同取值）；只有确实无法还原为公理投影的冲突，才动用裁决表（v4.5 14.7 保留为后备工具）。
4. **验证**：可疑参数降 C 级进假设登记簿，走统一验证规范；作者身份、收益展示、单次命中不构成证据。
5. **熔入**：验证通过后写进对应层，并**删除被替代的旧表述**——熔炉的标志是炉渣定期清出，而不是文件越长越好。

## 四、编号与引用规范（v1.1 立，v1.2 增第 5 条·版本存档）

> 为什么有这一章：拆分暴露了「编号＝身份」的脆弱性——**编号只是显示位置，会随重构变化；节名才是身份**。本章把编号管理制度化，今后任何结构重构照此办理，引用不再断链。

**五条规则（强制）**：

1. **节名永稳**：每节的「节名」（如「板块双口径观测」）一经命名永不改写；确需改名＝一次「重命名批次」，台账留痕。显示编号可变。
2. **只增不收**：已发布编号**永不复用、永不回收**；新增节只追加下一号——第三章统一语言现止于 3.10，若再新增即取 3.11，依此类推；删除的节保留空号并在台账登记原因。
3. **引用三件套**：跨文件引用必须写全「**文件名＋编号＋节名**」——正例「熔炼系统 3.4 板块双口径观测」；反例「只写 3.4」。引用 v4.5 的章节必须带「v4.5」前缀（如「v4.5 第十四章」），与自引用严格区分。
4. **重编号＝独立批次**：任何重编号单独立批（不夹带内容变更），跑 `scripts/check_refs.py` 全工作区校验（**0 ERROR 才算过**），台账登记新旧对照表，两文件版本号各 +0.01。**改号后引用不会自动跟着变**——这正是必须有第 3 条「节名」的原因：编号变了，节名还在，人和脚本都能靠节名把引用认回来。
   - 补节名可自动化：`python3 scripts/check_refs.py --fix` 只把「编号有效但缺节名」的引用补齐为三件套，**只补节名、不改编号**；存在 ERROR 时拒绝执行（旧号该映射成哪个新号必须人工判断，脚本猜错会把引用指向错误的节，比断链更危险）。跑完重跑一次确认 WARN 归零。
5. **每次发布必须存档（v1.2 立，用户 2026-10-18 定）**：版本号一旦变更，须把该版**完整快照**存入 `versions/`，命名 `<文件名>_v<版本号>_<发布日期>.md`；**旧版永不删除**（连"觉得改坏了"的版本也留——它记录了哪条路走不通）；**存档只读**，发现错误在新版改、不改旧档；**正文只保留现役版**（`熔炼系统.md` 永远是当前版本）。
   - 与 `.workbuddy/backups/` 的分工不可混：`versions/`＝**发布快照、供对照阅读**；`.workbuddy/backups/`＝**改动前工作备份、供误操作回滚**。两者互不替代。
   - 目的：**规则要能对照着看**——某条判断以前怎么写、改完是否真的更好，只有旧版在手才答得出；没有对照的迭代＝凭记忆自证。
   - 不追溯补档：本规则自 v1.14 起生效，此前版本无发布快照（散落在 backups 的是工作文件，不得冒充版本对照）。
