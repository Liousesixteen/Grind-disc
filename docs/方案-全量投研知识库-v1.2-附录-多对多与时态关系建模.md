# 全量投研知识库 v1.2 附录：多对多、时态与 n 元关系建模
## ——数据层多对多，展示层按需唯一；主存关系型，图能力用 networkx，RDF 作出口

> 本附录回答三个问题：①票与分类的多对多怎么做；②关系要不要上知识图谱；③Wiki/RDF 适不适合。

---

## 一、现状澄清：数据层已是多对多，"唯一"只发生在视图

| 层 | 关系 | 规模/现状 |
|---|---|---|
| 数据 | 票↔概念 | **120,444 条边**（一票 20–40 个概念） |
| 数据 | 票↔链·环节 | 多对多（主业链·环节、归因链·环节、概念映射链） |
| 数据 | 概念↔概念 | 多对多（别名/共现/领先） |
| 展示 | 主归属 / 归因 / 梯队桶 | **强制唯一**——"涨停家数"必须可加总，一票不能两桶各算一次 |

行业惯例同构：**行业分类唯一**（申万 31 一级、GICS 11 部门）；**概念/产业链多对多**（Wind、同花顺均允许一票多节点）。
所以正确表述是：**数据多对多，视图按权重坍缩为唯一**。

## 二、多对多要"真"，缺三样东西

| 缺口 | 现状 | 补法 |
|---|---|---|
| **角色 + 权重** | 边上只有"属于"，没有"怎么属于" | `role`（主营/参股/供货/合作/传闻/龙头/跟风）＋ `weight`（营收占比/关联度） |
| **时态** | 概念只有 first_seen/last_seen；边没有有效期 | 边上 `valid_from/valid_to`；查询一律按"当日有效"过滤 |
| **n 元关系（超边）** | 供货被压成二元边 | **事件具体化**：`supply_event` 节点 + 角色边（供货方/采购方/产品/金额/年度/是否关联方） |

调研依据（多源一致）：
- n 元关系推荐"具体化为中间节点"（Event Reification），RDF n 元类、属性图 reification 同理；
- 限定关系（qualified relation）承载时态/来源/置信度；
- 反模式：不要把所有关系都具体化（每次 +2 跳），只对真正的 n 元（供货/并购/中标）做；
- 不要把时间序列堆成节点属性（关系型/时序表更合适）。

## 三、统一边表（SQLite）

```sql
CREATE TABLE rel_edge(
  edge_id     INTEGER PRIMARY KEY,
  src_type    TEXT NOT NULL,      -- stock/concept/chain/segment/product/region/platform/event
  src_id      TEXT NOT NULL,
  rel_type    TEXT NOT NULL,      -- belongs_to/co_occur/alias/upstream/supplies/...
  dst_type    TEXT NOT NULL,
  dst_id      TEXT NOT NULL,
  role        TEXT,               -- 主营/参股/供货/合作/传闻/龙头/跟风
  weight      REAL,
  weight_unit TEXT,               -- '营收占比'/'共现率'/'相关系数'
  valid_from  TEXT,               -- ISO 日期
  valid_to    TEXT,               -- NULL = 至今
  source      TEXT,               -- 年报/招股书/公告/互动易/词表/统计
  confidence  TEXT,               -- A/B/C
  evidence    TEXT,               -- URL 或原文片段
  edge_group  TEXT,               -- n 元关系聚组（同一事件的多条角色边）
  created_at  TEXT
);
CREATE INDEX ix_edge_src ON rel_edge(src_type, src_id, rel_type, valid_to);
CREATE INDEX ix_edge_dst ON rel_edge(dst_type, dst_id, rel_type, valid_to);

-- n 元关系：事件节点（供货是五元组，不是两元）
CREATE TABLE rel_event(
  event_id    TEXT PRIMARY KEY,
  kind        TEXT,               -- supply/customer/contract/award/merger/policy
  date        TEXT,
  amount      REAL, amount_unit TEXT,
  product     TEXT,               -- 供的什么产品（可空）
  is_related  INTEGER,            -- 是否关联方
  source      TEXT, confidence TEXT, evidence TEXT
);
```

### 展示层唯一 → 视图

```sql
CREATE VIEW v_stock_primary AS
SELECT code, chain, seg FROM (
  SELECT src_id AS code, dst_id AS chain, weight,
         ROW_NUMBER() OVER (PARTITION BY src_id
                            ORDER BY weight DESC, valid_from DESC) AS rn,
         dst_id AS seg
  FROM rel_edge
  WHERE rel_type = 'stock_chain'
    AND (valid_to IS NULL OR valid_to > date('now'))
) WHERE rn = 1;
```

主归属、归因、梯队桶全部读视图；**数据不动，展示按需坍缩**。

## 四、四类关系在本系统中的落法

| 关系 | 建模 | role / weight | 证据 |
|---|---|---|---|
| 票↔概念 | 二元边 | role=主营/参股/供货/传闻；weight=营收占比或关联度 | 东财/同花顺 A；互动易 B |
| 票↔链·环节 | 二元边 × 两类（主业/归因） | 主业：weight=主营占比；归因：role=主业驱动/链内外溢/跨链 | F10 A；词表 B |
| 概念↔概念 | 二元边 | 别名/共现/领先；weight=共现率/领先天数 | 统计 A（事实）/C（解释） |
| **公司↔公司（供货）** | **事件节点 + 4 条角色边**（供货方/采购方/产品/金额） | is_related；amount | 公告 A；互动易 B |
| 席位↔票（资金） | 二元边 | role=买入/卖出；weight=金额 | 龙虎榜 A |
| 股东↔票（共持） | 二元边 | role=十大股东；weight=持股比例 | 定期报告 A |

## 五、要不要知识图谱 / Wiki（选型结论）

| 方案 | 优势 | 代价 | 结论 |
|---|---|---|---|
| **SQLite 边表 + 事件具体化** | 多对多/时态/n 元齐全；单文件、可备份、可 diff、SQL 可查 | 深遍历 >5 跳慢 | ✅ **主存储** |
| 属性图（Neo4j/ArangoDB） | 深遍历、路径、可视化 | 运维/备份/版本管理重 | 边 >100 万或需在线多跳时迁 |
| RDF/OWL + SPARQL（Wikidata 式） | 标准、跨库互联、本体推理 | 本体设计与查询门槛高 | ✅ **出口**：导出 TTL 子集供互联 |
| Wiki（MediaWiki/Wikidata 部署） | 众包治理、引用链、修订史 | 个人无社区；口径漂移；治理成本高 | ❌ 不建站；**借模型**：声明+引用+修订 |
| 超图库 | 原生 n 元 | 生态小、工具少 | ❌ 用事件具体化替代 |

**一句话**：图上要的是"能力"（多跳、社区、中心度），不必先上"图数据库"；Wiki 要的是"模型"（声明+引用+修订），不必先上"站点"。

## 六、升级触发条件（量化，不凭感觉）

1. 边数 > 100 万 → 迁 Neo4j/ArangoDB；
2. 需要在线多跳查询 <200ms（如看板点概念即时展开三级上下游）→ 迁图库或预计算物化路径；
3. 需要与外部图谱（Wikidata/深交所图谱）互联 → 导出 RDF 子集；
4. 团队/多人协作编辑 → 才考虑 Wiki 化（当前单人不触发）。

## 七、对现有资产的影响

- `universe.json` / `concept_map.json` / `name_clan`：成为边表的**导入源或物化视图**，字段不变；
- 主归属/归因/梯队：逻辑不变，改为读 `v_stock_primary`；
- 全量库 xlsx：从 DB 导出（单一事实源）；
- 新增：`rel_edge`、`rel_event`、`v_stock_primary`、`v_concept_chain` 四个对象，其余照 v1.1。
