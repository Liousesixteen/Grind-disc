# 技术演进与规模化方案 v1（2026-10-25）
## ——AI 选股与多用户服务的重新评估：现在不用换，但要知道何时换什么

> 背景：现有方案（Python + SQLite + networkx + Caddy + systemd，单机单用户）是按"个人盯盘"设计的。
> 本文评估两个未来场景：**A. AI 智能选股**（单用户/内部）、**B. 大规模多用户服务**，
> 并回答"知识图谱到底用不用 Neo4j"。

---

## 〇、结论先说

| 场景 | 现在这套够不够 | 需要换什么 | 触发时机 |
|---|---|---|---|
| 个人盯盘（现在） | 够 | — | — |
| **A. AI 选股（单用户）** | **够，只需加分析层** | DuckDB/Parquet 特征库 + LightGBM + 回测引擎 + LLM API | 想训练模型时 |
| **B. 多用户服务（100+）** | **不够** | PostgreSQL + Redis + FastAPI + 任务队列 + Docker | 并发写/多租户时 |
| 知识图谱 | 边表+networkx 够 | Neo4j 只在"在线多跳查询"时才值 | 见 §三 |

**不要提前迁移**：现在换 Postgres/Neo4j，只增加运维成本不增加能力。

---

## 一、场景 A：AI 智能选股（单用户）——加"分析层"，不动存储层

数据量级：A 股 5576 只 × 20 年日频 ≈ 2800 万行，加上概念/资金/行为特征 ≈ 1–2 GB。
**这个量级 SQLite/DuckDB 完全够**，不需要分布式。

| 层 | 技术 | 说明 |
|---|---|---|
| 特征库 | **Parquet + DuckDB** | 每日收盘后把个股×因子写成列存，按年分区；查询比 SQLite 快一个量级 |
| 因子/标签 | pandas/polars 计算 | 动量、波动、换手、连板、概念热度、龙头地位、错位度、**图谱中心度**、名字族 |
| 模型 | **LightGBM（LambdaRank 排序）** + 线性多因子做基线 | 排序任务比分类更贴近"选股"；小样本别上深度学习 |
| 回测 | **自研事件驱动**（或 vectorbt） | 必须含涨跌停不可成交、T+1、手续费/滑点；用 purged 时间序列交叉验证防泄漏 |
| LLM | **API 调用**（Claude/GPT/DeepSeek） | 只做"解释/摘要/事件抽取/RAG 检索"，**不直接预测价格**（幻觉不可控） |
| 向量检索 | **sqlite-vec 或 pgvector**（若上 PG） | 公告/新闻语义检索，做 RAG |
| 调度 | 现有 systemd timers | 收盘后：特征 → 打分 → 候选池；盘中只跑规则（低延迟） |

**关键设计**：
- AI 输出落在 `fact_ai_candidates(date, code, score, rank, reason, model_ver)`，看板只展示 Top-N；
- **模型版本与特征快照必须留档**（否则无法复盘"当时为什么选它"）；
- 盘中不做模型推理（延迟与稳定性），只做规则筛选 + 展示昨日模型候选。

## 二、场景 B：多用户服务——存储与服务层都要换

| 层 | 现在 | 多用户需要 | 为什么 |
|---|---|---|---|
| 数据库 | SQLite（WAL，单写者） | **PostgreSQL 16** | 并发写、行级锁、多租户、备份/PITR |
| 时序/分析 | — | **TimescaleDB 或 ClickHouse**（量大时） | 日频快照 + 分钟切片的分区与聚合 |
| 缓存 | 进程内存 | **Redis** | 会话、热点 API、限流计数、任务队列 |
| 任务队列 | systemd timer | **Celery/RQ + Redis** | 抓取/抽取/回测等异步任务，可重试可观测 |
| Web | http.server | **FastAPI + Uvicorn**（+ Gunicorn） | 异步、SSE/WebSocket、鉴权、OpenAPI |
| 鉴权 | BasicAuth | **JWT/OAuth2 + 租户隔离** | 多用户、权限、审计 |
| 部署 | 单机 systemd | **Docker Compose → K8s/云托管** | 多服务编排、滚动升级 |
| 监控 | healthz + 企微 | **Prometheus + Grafana + Loki** | 指标/日志/告警统一 |
| 网关 | Caddy | **Nginx/云 API 网关 + 限流** | 防刷、配额、WAF |

**成本曲线**（估算）：
- 10–50 用户：8C16G + 云 PG（2C4G）+ Redis（1G）≈ 600–1000 元/月
- 1000+ 用户：读写分离 + CDN + 队列扩容 ≈ 3000–8000 元/月

## 三、知识图谱：什么时候才需要 Neo4j

| 阶段 | 方案 | 够用性 | 触发升级 |
|---|---|---|---|
| 现在 | **SQLite 边表 + networkx** | 离线社区发现/中心度/多跳（<5 跳）都够 | — |
| AI 选股 | 仍够；**图谱特征离线跑**（中心度、社区标签、上下游距离 → 喂模型） | 图算法是批处理，不需要在线 | — |
| 多用户在线图查询 | **Neo4j（社区版）或 ArangoDB** | 需要 <200ms 的在线多跳、图算法 API 化 | ①在线图查询 QPS >10 ②边 >100 万 ③要看"路径解释"（A→B 为什么相关） |
| 需要与外部图谱互联 | 导出 **RDF（rdflib）** | 标准互通 | 对接 Wikidata/深交所图谱时 |

**Neo4j vs 替代**：
- Neo4j 社区版：单机免费、Cypher 成熟、GDS 图算法库完整 → **多用户阶段首选**；
- Postgres + Apache AGE：不新增数据库，但图算法弱、生态小；
- ArangoDB：多模型（文档+图），适合同时要文档存储；
- 结论：**现在边表+networkx；多用户且在线图查询成为刚需时上 Neo4j**，中间可用"预计算物化路径"过渡。

## 四、AI 选股 + 多用户叠加时的架构

```
采集（定时）→ 原始库（PG）→ 特征库（Parquet/DuckDB）→ 模型打分（离线）
                                    ↓
                           fact_ai_candidates（每日）
                                    ↓
浏览器/App ← API 网关（鉴权/限流）← FastAPI ← Redis 缓存 ← PG 读库
                                    ↓
                              Neo4j（图查询，可选）
```

- 模型与图算法**永远离线**，在线只查结果表；
- 在线服务与离线计算物理隔离（不同进程/队列），互不拖累。

## 五、合规红线（必须提前知道）

1. **向公众提供具体证券买卖建议 = 证券投资咨询业务，需要投顾牌照**。
   - 可以做：数据展示、指标计算、历史复盘、模型评分（标注"非投资建议"）；
   - 不可以：向他人推荐"买这只、那个价位"并收费/引流；
2. 行情数据商用需授权（东财/同花顺数据不能直接转售或对外提供）；
3. 多用户需做个人信息保护（账号、手机号）与数据安全等级保护评估。

**结论**：AI 选股先做"个人工具"；要对外服务，先解决牌照与数据授权，技术反而是最容易的部分。

## 六、分阶段路线（按触发条件升级，不提前）

| 阶段 | 触发 | 动作 | 工期 |
|---|---|---|---|
| P0 现在 | — | SQLite + networkx + systemd（已完成方案） | — |
| P1 AI 选股 | 想要模型打分 | Parquet/DuckDB 特征库 + LightGBM + 回测 + LLM API | 2–3 周 |
| P2 小团队 | 并发用户 >10 或需要多租户 | PG + Redis + FastAPI + Celery + Docker Compose | 2–3 周 |
| P3 规模化 | DAU >1000 或图查询在线 | K8s/云托管 + ClickHouse + Neo4j + 网关限流 | 1–2 月 |

**每阶段都可独立交付、独立回滚**；不做到下一阶段所需的能力，不提前引入对应技术。
