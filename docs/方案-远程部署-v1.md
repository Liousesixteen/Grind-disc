# 远程部署技术方案 v1（2026-10-25）
## ——单机云服务器为主，SQLite 主存，systemd 托管，HTTPS + 鉴权

> 背景：本机跑看板时合盖断网就失效。目标是把"采集 → 计算 → 存储 → 展示"整体搬到云服务器，
> 7×24 不受本机影响；本机降级为开发/离线查询环境。

---

## 一、目标与约束

| 项 | 要求 |
|---|---|
| 可用性 | 交易日 9:15–15:10 必须在线；服务器重启后自动恢复 |
| 实时性 | 盘中 15 秒刷新（服务端拉取），前端轮询或 SSE |
| 数据 | 全量库（SQLite）在服务器；每日备份到对象存储 + 本机 |
| 成本 | 起步 ≤ 200 元/月 |
| 安全 | 公网只开 443；看板必须鉴权；SSH 仅密钥 |
| 可回滚 | 本机随时可恢复接管（同一 git 仓库 + 数据备份） |

---

## 二、部署拓扑（单机三层）

```
                 ┌──────────── 云服务器（2C4G，Ubuntu 24.04，上海/深圳）────────────┐
  浏览器/手机 ──443──▶ Caddy（HTTPS 自动证书 + BasicAuth + gzip）
                       │
                       ├──▶ trading-board.service   （常驻：读内存 state，/api/state、/）
                       │        └─ 盘中每 15s：拉行情 → 计算 → state（不写库）
                       │
                       ├──▶ trading-collect.service （盘中每 5min：落轻量切片）
                       ├──▶ trading-pool.timer      （每交易日 15:05：股池全量）
                       ├──▶ trading-kb.timer        （每交易日 15:40：全量库/供需增量/主题树）
                       └──▶ trading-backup.timer    （每日 23:30：SQLite 备份 → COS/OSS + 本机）
                                        │
                                   SQLite（WAL，单写者）
```

- **唯一持久层**：`/srv/trading/cache/kb/trading_kb.sqlite`（WAL）
- **实时状态**：进程内存（现有 `Board.state`，逻辑不变）
- **图计算**：收盘后离线跑 networkx，结果写 `theme_tree` 表

## 三、规格与成本

| 项 | 建议 | 说明 |
|---|---|---|
| 服务器 | **2 核 4G / 80G SSD**，上海或深圳 | 轻量应用服务器即可；行情源国内节点延迟低 |
| 带宽 | 3–5 Mbps 峰值 | `/api/state` 350KB；开 gzip 后 ~50KB，15s 一次 ≈ 3KB/s |
| 系统 | Ubuntu 24.04 LTS | Python 3.11+ 原生 |
| 对象存储 | COS/OSS 标准存储 | 备份 1–2GB，几元/月 |
| 域名 | 一个二级域名（可选但推荐） | HTTPS 证书需要；也可用 IP + 自签（不推荐） |
| 成本 | 服务器 ~90–150 元/月 + 存储 ~5 元/月 | 2C4G 轻量常见价 |

## 四、部署方式对比（选 systemd）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **systemd + venv**（推荐） | 内存开销最小（无 Docker 层）；日志进 journald；单元文件即文档 | 环境靠脚本保证 | ✅ 单机首选 |
| Docker Compose | 环境可复现、易回滚 | 额外 200–400MB 内存；SQLite 挂载要注意 WAL 权限 | 多环境/多人时再上 |
| Kubernetes | 弹性 | 完全过度 | ❌ |

## 五、进程与定时任务（含交易日历）

| 单元 | 类型 | 时间 | 作用 | 失败策略 |
|---|---|---|---|---|
| `trading-board.service` | 常驻 | 开机即启 | 看板 HTTP + 15s 抓取 | `Restart=always`，60s 退避 |
| `trading-collect.service`+`.timer` | 定时 | 交易日 9:25–15:00 每 5 分钟 | 轻量切片落库 | 失败重试 2 次后记 warn |
| `trading-pool.service`+`.timer` | 定时 | 交易日 15:05 | 股池全量（现有 pool_pipeline） | 幂等，失败重跑 |
| `trading-kb.service`+`.timer` | 定时 | 交易日 15:40 | 概念增量/全量库/主题树/供需抽取 | 同上 |
| `trading-backup.service`+`.timer` | 定时 | 每日 23:30 | SQLite 备份 + 上传 + 校验 | 失败告警 |

**交易日历**：所有定时任务先查 `trade_calendar` 表（周末/节假日直接退出），不靠 `Mon-Fri` 猜——
节假日误跑会拉空数据并污染事实表。

时区统一 `Asia/Shanghai`；systemd 用 `OnCalendar=Mon..Fri *-*-* 09:25:00` + 脚本内日历二次校验。

## 六、数据与备份

| 项 | 策略 |
|---|---|
| 主库 | SQLite WAL，单写者（collect/pool/kb 串行） |
| 在线备份 | 每日 23:30 `sqlite3 .backup`（一致性快照，不锁库）→ `gzip` → 上传 COS/OSS，保留 30 天 |
| 本机副本 | 每日 rsync 拉回本机 `~/Finance/AI顶级交易员/backup/`，供离线查询/灾备 |
| 导出 | 每周从 DB 重出 xlsx 全量库（现 `export_workbook.py`），一并备份 |
| 恢复演练 | 每月一次：用备份在临时目录起库，跑 `--verify-uni` 与三条 SQL |
| 数据量 | 日增 ~5.8 万行 / 3–5MB；一年 1–1.5GB（80G 盘充足） |

## 七、网络与安全

1. **只开 443**（Caddy 自动 Let's Encrypt），80 仅做跳转；
2. **鉴权**：Caddy `basic_auth`（用户名+强密码），或一次性 token URL（`/?k=...`）两种任选；
3. **SSH**：仅密钥登录、禁 root 密码、`ufw` 限源 IP、`fail2ban`；
4. **行情源**：云服务器访问东财/新浪通常正常，但云 IP 可能被限流 → 保持现有"退避 + 多源 + 缓存"策略，抓取间隔不低于 15s，不并发轰炸；
5. **DB 不对外**：SQLite 是文件，天然不可远程直连；只通过看板接口暴露聚合结果；
6. **密钥**：全部放 `/etc/trading/env`（600），不进 git。

## 八、可观测与告警

| 项 | 做法 |
|---|---|
| 健康检查 | `GET /healthz` 返回 `{ok, taken_at, lag_s, db_ok}` |
| 告警渠道 | 企业微信机器人 webhook（或 Server 酱/邮件） |
| 告警规则 | ①进程不在 ②连续抓取失败 ≥3 次 ③`lag_s > 120` ④磁盘 >80% ⑤备份失败 |
| 日志 | journald 保留 7 天；关键事件写 `logs/` 轮转 |
| 心跳 | 每 5 分钟写 `heartbeat` 表；外部监控可读 |

## 九、迁移步骤（本机 → 服务器）

1. **准备**：买 2C4G；装 Ubuntu 24.04；`timedatectl set-timezone Asia/Shanghai`；2G swap；
2. **基线**：建用户 `trader`、SSH key、ufw（只开 22/80/443）、fail2ban；
3. **代码**：`git clone`（或 rsync 整目录，排除 `cache/` 大文件与 `.venv`）；建 venv 装依赖（生成 `requirements.txt`）；
4. **数据搬迁**：`rsync -av cache/ server:/srv/trading/cache/`（pool_*、theme_universe、intraday 约数百 MB）；
5. **初始化 DB**：跑 `kb_build.py`（P1 完成后）或先用 JSON/CSV；
6. **systemd 单元**：5 个 unit + 4 个 timer，`enable --now`；
7. **反向代理**：Caddyfile（反代 6060、basic_auth、gzip、`encode zstd gzip`）；
8. **验证**（交易日盘中）：`/healthz` 200、`/api/state` 350KB、看板打开、日志无报错、连续 3 次刷新 `lag_s < 30`；
9. **切流量**：本机停看板 → 书签改为域名；本机保留为开发环境，只读备份库；
10. **回滚**：本机 `systemd` 或手动启动即可接管（DB 用当日备份）。

## 十、与现有纪律的冲突与调整

| 现有纪律 | 远程部署后 |
|---|---|
| "不设定时任务、看板手动启动" | 服务器上必须反过来：systemd 常驻 + timer 定时；本机仍保持手动（开发态） |
| "依赖装本地 .venv" | 服务器同样用 venv，路径 `/srv/trading/.venv` |
| 四时点落档 | 由 `trading-collect` 与 board 内部逻辑共同保证，档仍在 `cache/intraday/` |
| 数据只在本机 | 服务器为主库，本机为副本（单向同步，不双写） |

## 十一、演进路线

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 单机（本方案） | 当前 | 2C4G + SQLite + Caddy |
| 拆分 | 盘中 CPU 峰值 >70% 持续，或供需抽取拖慢 | 采集/计算独立容器；SQLite → Postgres |
| 图分析独立 | 边 >100 万、需在线多跳 | Neo4j/ArangoDB，DB 只同步结果 |
| 多端 | 需要手机原生/多人协作 | 前端 SPA + API 网关；权限与审计 |

## 十二、风险清单

| 风险 | 缓解 |
|---|---|
| 云服务器 IP 被行情源限流 | 多源 + 退避 + 缓存；必要时换弹性 IP |
| SQLite 写锁 | WAL + 单写者 + `busy_timeout`；写任务串行 |
| 服务器重启后未自启 | `systemctl enable`；开机自检脚本 |
| 备份不可用 | 每月恢复演练；备份校验 `PRAGMA integrity_check` |
| 公网暴露 | 仅 443 + BasicAuth + fail2ban；日志审计 |
| 云厂商磁盘故障 | 每日异地备份；DB 可从原始缓存重建 |
